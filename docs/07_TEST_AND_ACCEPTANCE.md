# 07. План тестирования и приёмки

Тестовый контур: автоматические unit-тесты доменной логики, интеграционные тесты с PostgreSQL, имитация Discord interactions, отдельный закрытый Discord test-guild для ручной проверки UI. Не использовать реальные деньги и настоящие балансы участников.

## 7.1. Обязательные инварианты

- **INV-01:** В каждой финансовой операции сумма `ledger_entries.delta` равна нулю.
- **INV-02:** Баланс каждого обычного счёта >=0; системный эмитент — единственное специально обоснованное исключение.
- **INV-03:** Одна уникальная операция не может быть выполнена дважды по одному idempotency-key.
- **INV-04:** Одна регистрация на `(guild_id, discord_user_id)`; один стартовый перевод на гражданина.
- **INV-05:** Один уникальный объект имущества имеет ровно одного текущего владельца.
- **INV-06:** Ни один платёж бюджета не превышает доступную статью и остаток казны.
- **INV-07:** Нельзя повторно выплатить одно рабочее задание/контракт/зарплатный период.
- **INV-08:** Смена ставки налога не пересчитывает завершённые и уже принятые сделки.
- **INV-09:** Политическая игровая роль не предоставляет системных Discord-прав владельца.
- **INV-10:** Нет рабочих платежей/изменения власти без полномочий, все исключения аудируются.
- **INV-11:** Сбой Discord при уведомлении не приводит к повторному денежному переводу.
- **INV-12:** Не происходит случайной эмиссии через задания/зарплаты/сделки.

Для D-10 проверьте, что первый срыв требует независимого подтверждения и позволяет открыть одну связанную повторную попытку. Второй подтверждённый срыв отображается как игровой кризис. До его закрытия третья попытка по той же должности отклоняется. Для другой должности выборы остаются доступны, а сроки записанных мандатов сохраняются. Для D-11 проверьте, что собственное предложение о закрытии кризиса подтвердить нельзя, а независимое подтверждение оставляет обе записи в аудите и разрешает новый цикл. Публичный результат показывает закрытие кризиса.

## 7.3. Проверка бизнес-сценария end-to-end

**В тестовом сервере:**

1. Зарегистрировать граждан A и B; проверить +250 каждому и казну +8000 (начальный genesis только однажды).
2. A выполнить NPC-работу с вознаграждением 30: A +30, казна −30, лимит NPC −30.
3. B открыть компанию за 150: B −150, казна +150.
4. A покупает услугу компании B за 200: после финансирования в эскроу 200, после принятия заказ распределяет +180 компании и +20 казне.
5. A либо B купить доступный уникальный объект государственного имущества за объявленную сумму; проверить право собственности.
6. Уполномоченный чиновник публикует отчёт бюджета; все цифры совпадают с journal.
7. Перезапустить бота и повторить все подтверждающие кнопки; баланс и собственность не изменяются.

Проверка не должна зависеть от внешнего EasyPoll: избирательные протоколы тестируются отдельно через локальный stub/имитацию подтверждения.

### Прогон с владельцем в закрытой Discord-гильдии

Используйте отдельную тестовую БД, тестового бота и 2–3 участников. Для проверки выборов нужны два независимых проверяющих и кандидат. Роли гражданина, президента и депутата должны быть отдельными игровыми ролями ниже роли бота. Проверьте права ролей в настройках сервера, каналов и категорий. Оставьте у бота `Manage Roles` для синхронизации и отключите `Administrator`. Зафиксируйте хеш коммита, версию PostgreSQL, ревизию Alembic и включённые модули. Токен и строки подключения в протокол не включаются.

| Шаг | Действие | Что записать в протокол |
|---|---|---|
| 1 | Проверить команды и кнопки на русском и английском. Зарегистрироваться, повторить регистрацию, выйти и вернуться при включённом учёте членства | Языки, статус, выдача и снятие роли, тот же ID гражданина и неизменный стартовый грант |
| 2 | Отправить перевод и открыть свою квитанцию. Проверить ещё одним участником тот же номер | Один платёж, правильные знаки суммы у сторон, отказ в просмотре постороннему, нейтральный текст личного уведомления |
| 3 | Выполнить NPC-работу, зарегистрировать фирму, оформить продажу с налогом, принять разовое задание. Двум покупателям одновременно подтвердить один объект | Суммы до и после, уникальные номера платежей, один владелец объекта, один платёж за работу |
| 4 | Создать контракт, зарезервировать оплату, сдать работу и принять её. Сверить `/treasury report` с проводками | Казна, статьи, резервы, налоги и эмиссия; отсутствие личных данных в отчёте |
| 5 | Вручную записать внешний протокол и подтвердить другим членом комиссии. Проверить попытку утверждения бюджета обычным игроком | Снимок допуска, агрегаты, два независимых актора, срок мандата, отказ и аудит попытки расхода |
| 6 | Включить `/admin maintenance`, проверить блокировку нового перевода и доступность истории. Перезапустить бота и проверить состояние, очереди, остатки и владение. Снять паузу и восстановить тестовую копию на отдельной БД | Отказ до проводки, доступность истории, оба переключения в `/admin audit`, сохранившиеся записи, отсутствие повторных платежей и результат восстановления |

#### Настройки репетиции на троих

Назначьте A, B и C в `CIVITAS_ALLOWED_USER_IDS` и `CIVITAS_ELECTION_COMMISSIONER_IDS`. A баллотируется в президенты, B в парламент, C владеет компанией. Для репетиции задайте `CIVITAS_ELECTION_MIN_ELIGIBLE=3`, `CIVITAS_ELECTION_QUORUM_MIN=2`, `CIVITAS_ELECTION_QUORUM_BP=4000`, `CIVITAS_ELECTION_PARLIAMENT_SEATS=1`, `CIVITAS_ELECTION_VOTING_HOURS=1` и `CIVITAS_ELECTED_TREASURY=true`. B проверяет NPC-задания, C выставляет тестовое имущество и выполняет обязанности технического оператора. Выделите отдельный текстовый канал для отчёта.

После регистрации откройте оба голосования одновременно. B открывает президентские выборы и записывает итог, A делает это для парламентских. C подтверждает оба результата. Используйте две разные ссылки на опросы разрешённого хоста и фактические агрегаты голосов. Сначала проверьте отказ, когда итог пытается подтвердить тот же участник, который его записал. Пока идёт голосование, выполните экономические шаги 2–3. На пустой тестовой БД мандаты начинают действовать после подтверждения. После этого A создаёт контракт, B утверждает статью и резервирует средства, C сдаёт работу, B подтверждает оплату компании. Попытка C утвердить бюджет должна получить отказ, который C увидит в приватном аудите.

Проверяющие отмечают каждый шаг как пройденный, не пройденный или отложенный с причиной. Допуск к первому сезону фиксируется после проверки и согласования открытых правил из раздела 09.

## 7.4. Разделение тестов

- Unit: налогообложение, разрешённые переходы статусов, валидация бюджетов, RBAC.
- Integration: реальные PostgreSQL transactions, concurrent transfers, unique constraints, повторная выдача, row-locks, backfill.
- Discord stub: обработчики взаимодействий, ephemeral, ошибки прав, идентификаторы.
- Для гражданства Discord stub проверяет RU/EN для ответов и описаний, английский для остальных локалей, выдачу и снятие настроенной роли по статусу, повтор после сбоя и отсутствие изменений при совпадении роли со статусом.
- Manual test-guild: roles, button click, timeout, text length, accessibility.
- Recovery: DB backup/restore, повтор worker после kill, отказ сети Discord.

## 7.5. Definition of Done по любой финансовой функции

- Есть явный use-case с предусловиями и последствиями.
- Есть unit-тест на основной сценарий, ошибки и повторы.
- Есть integration-тест конкурирующих запросов и атомарности.
- Данные не меняются при отказе до commit; после commit — уведомления могут ретраиться безопасно.
- Изменения отражены в документации, миграции проходят на чистой БД.
- Проведена сверка журнала и балансов.
